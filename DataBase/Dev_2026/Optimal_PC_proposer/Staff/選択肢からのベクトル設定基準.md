# 選択肢からのベクトル設定基準

**版:** 運用実装基準 v0.5（NPU TOPS・電源なし利用・静音希望を反映）
**用途:** 接客時の希望条件を、PCの数値スペックと照合できる「要求ベクトル」に変換する。顧客QRは現行 version 5（30数値フィールド）を発行し、スタッフページは旧version 1〜4も後方互換で読み取る。

> この基準は固定正規化範囲を用いる初期運用案です。カタログの正本はFirebase Cloud Firestoreです。2026-10-26の読取確認時点では `pc_catalog` は0件でした。実機のおすすめはFirestoreに有効なPC商品文書が登録されるまで表示されません。ベンチマーク変換アンカーと販売員の主観評価は実製品データに応じて見直してください。

## 1. ベクトルの定義と曖昧さの扱い

指定された14個の重みと対応させるため、顧客ベクトルとPCカタログの両方を次の**14成分**に固定します。値は順序付きの数値列です。

| # | キー | 意味・単位 | 顧客側の値の意味 |
|---:|---|---|---|
| 1 | `cpuSingle` | Cinebench 2026 single-core score | 希望する性能の目安 |
| 2 | `cpuMulti` | Cinebench 2026 multi-core score | 希望する性能の目安 |
| 3 | `npuTOPS` | NPU性能（TOPS） | 顧客側は希望する最低TOPS値（0は特別な希望なし）、商品側は実TOPS値（0はNPU非搭載） |
| 4 | `gpu` | 3DMark Steel Nomad score | 希望する性能の目安。グラフィックス負荷がなければ0 |
| 5 | `ramGB` | RAM（GB） | 希望容量 |
| 6 | `ssdGB` | SSD（GB） | 希望容量 |
| 7 | `weightG` | 重さ（g） | 希望する重さの上限／目標。小さいほど軽い |
| 8 | `design` | デザイン評価（1～10） | 外観重視度から置く仮の目標点 |
| 9 | `displayInch` | 画面サイズ（inch） | 希望する画面サイズ |
| 10 | `aspectRatio` | 画面比率の数値 | 16:9は16÷9 = 1.777778、16:10は16÷10 = 1.600000 |
| 11 | `manufacturerMask` | メーカー選択のビットマスク（整数） | 0は指定なし。複数選択をビット集合として保持 |
| 12 | `failureFrequency` | 故障頻度カテゴリ | 0 = 少ない、1 = 多い |
| 13 | `readability` | 画面の見やすさ評価（1～10） | 希望する目安点 |
| 14 | `positioning` | 製品位置付け評価（1～10） | 1 = エントリー、10 = ハイエンド |

NPUは第3成分をTOPS値で表し、独立した「NPU搭載」フラグは追加しません。商品データのTOPS値0はNPU非搭載、0より大きい値は性能値が登録されたNPU搭載を表します。顧客要求ベクトルの0はNPU非搭載を希望する意味ではなく、TOPS性能に特別な希望がない状態を表します。これにより14成分・指定された重みの順番を保ちます。

アスペクト比を1.777778／1.600000で持ちますが、これは連続的な数値ではなくカテゴリです。正規化後に数値距離として比較せず、16:9同士／16:10同士かを判定します。メーカーも順位のある数値ではなくカテゴリです。選択肢の複数選択を失わないよう、メーカーはビットマスクで保持します。

質問14の文面は「故障が少ないPCが欲しいか」だけでなく価格とのトレードオフを選ぶ形式です。この試作では、選択肢A「値段は高いが故障事例が少ない」を故障頻度0、選択肢B「値段は安いが故障事例が多い」を故障頻度1として、そのまま希望カテゴリにします。これは設問の二者択一を尊重した暫定解釈であり、故障が多いPCを希望として扱う点が直感と合わない可能性があります。運用前に、設問を「故障しにくさをどれくらい重視するか」へ変更するか確認してください。

## 2. ベクトルの集約方針

回答の単純平均は採用しません。CPUスコア、GB、g、カテゴリ値の尺度や意味が異なるうえ、複数用途の平均を取ると「ゲームとWeb閲覧を両方する」人のゲーム性能要求が平均で薄まるためです。試作では、要求性能・容量は原則として選択された用途の**最大要求（max）**を採用し、画面サイズ・外観評価など選択肢が直接指定する項目は規則で決めます。複数用途を選んでも高負荷用途を弱めません。

`purposeBase` は仕事0.35、勉強0.28、趣味・娯楽0.40とします。複数選択時は最大値です。作業ごとの `taskCpu` と `taskGpu`、マルチタスク・利用年数による加算を以下の表で得ます。

| 質問5の作業 | `taskCpu` | `taskGpu` | RAMの最低目安 | SSDの追加条件 |
|---|---:|---:|---:|---|
| ウェブ検索 | 0.24 | 0 | 8GB | なし |
| メールの送受信 | 0.22 | 0 | 8GB | なし |
| 文書作成・編集 | 0.30 | 0 | 8GB | なし |
| 表計算・データ管理 | 0.42 | 0 | 16GB | なし |
| プレゼンテーション資料作成・発表 | 0.42 | 0 | 16GB | なし |
| 画像・動画の編集 | 0.78 | 0.74 | 32GB | 少なくとも1024GB |
| SNS・ブログの更新 | 0.30 | 0 | 8GB | なし |
| ネットショッピング・銀行決済 | 0.22 | 0 | 8GB | なし |
| オンライン会議・通話 | 0.40 | 0 | 16GB | なし |
| ゲーム | 0.72 | 0.86 | 32GB | 少なくとも1024GB |
| 動画視聴 | 0.32 | 0 | 8GB | なし |
| プログラミング | 0.70 | 0 | 16GB | なし |

`Dcpu = clamp(max(purposeBase, 選択した作業のtaskCpu最大値) + 年数加算 + マルチタスク加算, 0.20, 1.00)` とします。年数加算は3年未満0、3～5年0.05、6～12年0.10。マルチタスク加算は「ほとんどしない」0、「たまにする」0.06、「頻繁にする」0.13です。添付実機CSVに合わせた現行の元スコア目標は `cpuSingle = round(60 + 650 × Dcpu)`、`cpuMulti = round(100 + 4000 × Dcpu)` とします。単純なCPU需要の下限Dcpu=0.20でもsingle 190点・multi 900点、高負荷では最大710点・4100点となり、添付の上位CPU（single 642点、multi 3450点）と比較できる尺度です。

位置付けの年数基礎点は3年未満4、3～5年6、6～12年8です。CPU需要が高い場合も一定以上の製品クラスを想定し、`positioning = max(yearsPosition, Dcpu >= 0.72 ? 8 : yearsPosition)` とします。したがって、期間が短くても高負荷作業を選び `Dcpu` が0.72以上なら、位置付け目安は8になります。

GPUは質問5の作業で最大の `taskGpu` を使います。動画編集・ゲームのどちらも選んでいない場合はGPU要求を0とし、それ以外は `gpu = round(80 + 3000 × taskGpu)` とします。添付CSVの内蔵GPU相当120〜250点と外付けGPU搭載機2650点を分離でき、ゲーム要求（taskGpu=0.86）は2660点となります。電源なし利用（質問9）と静かな環境での作業（質問11）は、NPU利用を優先して効率・発熱・ファン動作を抑えたい希望の代理指標として、NPU必要TOPS値に反映します。NPU自体はバッテリー容量・画面消費電力・製品冷却設計などを置き換えるものではないため、実駆動時間とファン音を保証する値ではありません。

顧客側NPU希望値はTOPS単位です。質問6が「6～12年」で、かつ質問5に画像・動画編集／オンライン会議／プログラミングのいずれかがある場合に基礎需要10 TOPS、それ以外は0です。質問9（電源なし利用）と質問11（静かな環境で作業）の頻度加算はそれぞれ「ほとんどしない」0、「たまにする」10、「頻繁にする」20 TOPSです。`npuTOPS = min(50, 基礎需要 + Q9加算 + Q11加算)` とし、添付実機の最大50 TOPSに合わせた初期要求上限です。

RAMの基礎目安は質問1で選択した用途の最大値（仕事16GB、勉強8GB、趣味・娯楽16GB）と、質問5の表、質問7の最低値（ほとんどしない8GB、たまにする16GB、頻繁にする32GB）の最大値です。質問6が6～12年なら最低16GBとします。要求目安は取り扱いやすい候補容量8／16／32／64GBのうち、上記を満たす最小容量に切り上げます。SSDは質問8の頻度により256／512／1024GB（ほとんどしない／たまにする／頻繁にする）とし、画像・動画編集またはゲームが選ばれていれば最低1024GBへ切り上げます。

### メーカーのビットマスク

選択肢の順序に1始まりのビット番号を割り当てます。複数選択時に選択済みビットをOR（または加算）します。

| bit | メーカー | bit | メーカー |
|---:|---|---:|---|
| 1 | Apple | 9 | Lenovo |
| 2 | NEC | 10 | HP |
| 3 | 富士通（FMV） | 11 | Dell |
| 4 | dynabook | 12 | MSI |
| 5 | パナソニック（レッツノート） | 13 | Acer |
| 6 | VAIO | 14 | マウスコンピューター |
| 7 | Microsoft（Surface） | 15 | chromebook（ブランドではなく製品カテゴリ） |
| 8 | ASUS |  |  |

選択メーカーを `i` としたとき、マスクは `Σ 2^(i−1)` です。例：Apple（bit 1）＋Dell（bit 11）＝1 + 1024 = 1025。カタログ側の1メーカーは同じ番号の単一ビットで表します。カタログ比較では顧客マスク0なら一致度1（指定なし）、指定ありなら顧客マスクと製品マスクのビットANDが0より大きいと1、そうでなければ0とします。「複数メーカー指定」はいずれかに一致すればよいという解釈です。

## 4. 0～1正規化と一致度

個人ごと・カタログごとに最小最大値を取り直すと、同じ顧客の値がカタログ更新で変わり、値の大きなGPU等が比較を支配します。したがって、カタログ全体の実データから毎回min/maxを再計算せず、全顧客・全製品に共通の**固定範囲**で線形正規化します。範囲外の値は0または1にクリップします。

| 数値項目 | 2026-10添付実機CSVに合わせた固定範囲 `min…max` | 正規化式 |
|---|---:|---|
| CPU single | 0…700 | `x / 700` |
| CPU multi | 0…4000 | `x / 4000` |
| NPU TOPS | 0…60 | `x / 60` |
| GPU Steel Nomad | 0…3000 | `x / 3000` |
| RAM | 4…64GB | `(x−4) / 60` |
| SSD | 128…2048GB | `(x−128) / 1920` |
| 重量 | 700…2500g | `(x−700) / 1800` |
| デザイン・見やすさ・位置付け | 1…10 | `(x−1) / 9` |
| 画面サイズ | 13.3…16inch | `(x−13.3) / 2.7` |
| アスペクト比 | 1.6または1.777778 | 数値min-maxではなく同カテゴリ判定 |
| メーカー | 0～32767ビットマスク | 数値min-maxではなくカテゴリ集合判定 |
| 故障頻度 | 0または1 | 数値min-maxではなく同カテゴリ判定 |

添付CSVの8機種はCPU single 108〜642、CPU multi 500〜3450、GPU 120〜2650、RAM 16〜32GB、SSD 256〜1024GB、重量1570〜2250gでした。従来の上限（CPU single 3000、multi 40000、GPU 25000、RAM 128、SSD 8192、重量3000）では実機の最大値でもCPU single 0.21、CPU multi 0.09、外付けGPU 0.11、RAM 0.23、SSD 0.11に圧縮されていました。新範囲ではそれぞれ0.92、0.86、0.88、0.47、0.47となり、外付けGPUと内蔵GPU、上位CPUと価格重視CPUの差が推薦に反映されます。重量2250gは0.86となり、軽量希望との不一致をより明確にします。

このCSVは上位機種寄りの8機種だけで、市場全体の代表標本ではありません。固定範囲は現カタログと今回のユーザー評価に対する暫定校正であり、より高いCinebench/Steel Nomad値、64GB超RAM、2TB超SSD、2500g超の製品を追加する際には、顧客・スタッフ両方の範囲と回答目標値を一緒に再評価してください。範囲外は従来どおり0または1にクリップします。Cinebench/Steel Nomadの版やテスト条件を混在させないでください。


## 5. 重み付けとPCランキング

指定された14項目の順番で、次の重みをそのまま使います。

| # | 項目 | 重み |
|---:|---|---:|
| 1 | CPU single | 1.00 |
| 2 | CPU multi | 1.00 |
| 3 | NPU TOPS | 0.80 |
| 4 | GPU | 0.60 |
| 5 | RAM | 1.00 |
| 6 | SSD | 0.90 |
| 7 | 重量 | 0.70 |
| 8 | デザイン | 0.50 |
| 9 | 画面サイズ | 1.00 |
| 10 | アスペクト比 | 0.70 |
| 11 | メーカー | 0.65 |
| 12 | 故障頻度 | 0.55 |
| 13 | 画面の見やすさ | 0.65 |
| 14 | 位置付け | 0.50 |

合計重みは **10.55** です。数値成分は第4節の固定範囲でそれぞれ0〜1へ正規化します。NPU以外の数値成分は成分一致度を `s_i = 1 − |normalize(customer_i) − normalize(pc_i)|` とします。NPUは必要TOPS値への一方向の充足度として、`required=normalize(customerNpu)`、`available=normalize(pcNpu)`、`s_NPU = required=0 ? 1 : 1 − max(0, required−available)` とします。希望より多いNPU TOPSは不足ではないため満点1で、余剰をさらにボーナスにはしません。アスペクト比と故障頻度は同一カテゴリなら1、異なれば0。顧客メーカーmaskが0（指定なし）ならメーカー一致度1、希望メーカー指定がある場合は顧客maskと製品maskに共通bitがあれば1、なければ0です。chromebook bitは選択肢の製品カテゴリとして通常のメーカー集合に含めます。

製品 `p` の一致度は `match(p) = 100 × Σ(w_i × s_i) / 10.55`。全14成分が必須なので、欠損値を0点にしたり都合よく分母から除外したりせず、無効な商品行として扱います。高一致度順に並べ、同率は型番の日本語照合順、次にJANの文字列昇順で安定化します。NPU以外の数値は不足・超過を同じ絶対距離とする近さの指標です。NPUのみ要求TOPS値を下回る不足を一方向に評価し、要求以上のTOPS値は満点とします。

顧客ページは一致度上位3機種、スタッフページは上位5機種を表示します。同じFirestoreカタログ、正規化範囲、カテゴリ規則、重み、同率順を両方のページに実装しています。顧客側は商品紹介 `highlights`、仕様の短い抜粋、一致度、JANバーコード画像（数字を画像に印字しない）を表示します。スタッフ側は14項目の仕様、一致度、`highlights`、JAN数字と「JANをコピー」ボタンを表示します。

## 6. 数字だけを含むQRの新形式

新QRは**数字とカンマだけ**からなる1行CSVです。version 5は30個の数値で、先頭が版番号 `5`、続く14項目が希望ベクトル、最後の15項目が質問回答コードです。新しい顧客ページはversion 5を生成します。第3成分のNPU希望値はTOPSです。フィールド数・順序・質問コード・数値だけという条件は従来と同じです。

```csv
5,600,3400,50,2660,32,1024,1520,6,14,1.600000,0,0,9,8,5,2,3,1,37,2,3,2,3,1,3,2,5,1,2
```

version 1の旧14値、version 2/3/4/5の30値をスタッフページで読み取れます。version 2〜4の旧NPU成分は当時の「コア」要求を表しTOPSと同一単位ではないため、質問回答コード（Q5、Q6、Q9、Q11）からTOPS希望を再計算します。質問回答がないversion 1ではNPU TOPS希望を0（指定なし）とします。version 2/3のCPU/GPU値は既存の旧スケール換算も行います。


## 7. 質問・選択肢の固定番号表

Q番号は顧客ページの質問順で1始まりです。単一選択は選択肢順に1, 2, ... を割り当てます。複数選択は選択肢順のbit 0, 1, ... に対応する値 `1, 2, 4, 8, ...` のbitmaskとし、複数選択の値はbitの論理和です。選択肢そのものは顧客QRに入りませんが、この表と同一表をスタッフ用decoderにも定義します。

| Q | 質問 | 選択肢の内部番号 |
|---:|---|---|
| 1 | 主な用途（複数選択） | bit値 1=仕事、2=勉強、4=趣味・娯楽。例：仕事＋趣味・娯楽は `1 OR 4 = 5`。必須で0不可。 |
| 2 | 持ち運び頻度 | 1=ほとんど持ち運びはしない、2=週1〜3日は持ち運びする、3=週4〜7日は持ち運びする。 |
| 3 | 重さの希望 | 1=重さは気にしない、2=重い方が良い、3=軽い方が良い。 |
| 4 | 画面の大きさ | 1=一度にたくさんの情報を表示したい、2=少しでも小型なパソコンが良い。 |
| 5 | パソコンでする作業（複数選択） | bit値 1=ウェブ検索、2=メールの送受信、4=文書作成・編集、8=表計算・データ管理、16=プレゼン資料作成・発表、32=画像・動画編集、64=SNS・ブログ、128=ショッピング・銀行決済、256=オンライン会議、512=ゲーム、1024=動画視聴、2048=プログラミング。必須で0不可。 |
| 6 | 使い続けたい年数 | 1=3年未満、2=3〜5年、3=6〜12年。 |
| 7 | マルチタスク頻度 | 1=ほとんどしない、2=たまにする、3=頻繁にする。 |
| 8 | 保存頻度 | 1=ほとんどしない、2=たまにする、3=頻繁にする。 |
| 9 | 電源に接続しない使用頻度 | 1=ほとんどしない、2=たまにする、3=頻繁にする。 |
| 10 | デザイン重視度 | 1=ほとんど重視しない、2=少し重視する、3=かなり重視する。 |
| 11 | 静かな環境で作業する頻度 | 1=ほとんどしない、2=たまにする、3=頻繁にする。 |
| 12 | 画面の見やすさ | 1=特にない、2=見やすい方が良い。 |
| 13 | メーカー（複数選択・任意） | bit値 1=Apple、2=NEC、4=富士通（FMV）、8=dynabook、16=パナソニック（レッツノート）、32=VAIO、64=Microsoft（Surface）、128=ASUS、256=Lenovo、512=HP、1024=Dell、2048=MSI、4096=Acer、8192=マウスコンピューター、16384=chromebook。指定なしは0。 |
| 14 | 価格と故障頻度 | 1=値段は高いが故障事例が少ない、2=値段は安いが故障事例が多い。 |
| 15 | 保証の希望 | 1=メーカー保証で十分、2=物損保証を追加したい、3=何でも守れる保証が良い、4=今はまだ決めていない。 |

Q13の回答bitmaskは顧客ベクトル第11成分 `manufacturerMask` と同じ選択肢順です。ただしQR内にはベクトル用項目と回答コード用項目の両方が入り、Q13回答そのものも独立に復号できます。Q1・Q5は顧客フローで少なくとも1つ選ばれる前提です。Q13だけは任意選択で、0を許可します。

## 8. 共有PCカタログ（Firebase Cloud Firestore）

PC商品カタログの正本はFirebaseプロジェクト `optimal-pc-proposer` のCloud Firestore、コレクション `pc_catalog` です。顧客ページとスタッフページはFirebase JavaScript SDK 13.1.0を使い、どちらも同じコレクションから商品を読み込みます。従来のGitHub `pc_data/`、日時付きCSV一覧、GitHub Contents API、`latest.json` はカタログ読込・保存には使用しません。CSVダウンロードはバックアップとして残します。

各Firestoreドキュメントは1機種を表し、ドキュメントIDはJAN文字列と同一です。JANは数値でなく文字列として保存し、先頭ゼロを失わないようにします。ベクトル14項目の順序はこれまでと同じで、旧CSVで `npuCores` と命名されていた第3項目だけを、実値が示す単位に合わせて `npuTOPS`（NPUの演算性能、TOPS）へ改名します。添付された8機種の `npuCores` 列値 `[50,50,50,49,46,0,0,0]` はすべてTOPS値として扱います。旧Firestore文書に `npuCores` が残っていても両ページは読み取り時に `npuTOPS` として解釈し、新規書込み・CSVバックアップ見出しでは `npuTOPS` を使います。

```text
model,jan,cpuSingle,cpuMulti,npuTOPS,gpu,ramGB,ssdGB,weightG,design,displayInch,aspectRatio,manufacturerMask,failureFrequency,readability,positioning,highlights
```

`model`、`jan`、`highlights` は文字列、ベクトル14項目は数値です。`highlights` は500文字以内です。Firestoreフィールドに順序はありませんが、CSVバックアップは上記17列の並び、JAN文字列、14ベクトル値を維持します。古いCSVは商品カタログを読み込む経路には使わず、必要な値をスタッフ画面から登録してください。

### 8.1 実機データに基づく初期正規化基準

2026-10-24の実機CSV8機種を暫定基準にしました。CPU singleは108〜642、multiは500〜3450、GPUは120〜2650、RAMは16〜32GB、SSDは256〜1024GB、重量は1570〜2250g、NPU TOPSは0〜50です。初期マッチング用の固定範囲は、ベクトル順に CPU single `[0,700]`、CPU multi `[0,4000]`、NPU TOPS `[0,60]`、GPU `[0,3000]`、RAM `[4,64]`、SSD `[128,2048]`、重量 `[700,2500]`、デザイン `[1,10]`、画面インチ `[13.3,16]`、画面比率・メーカー・故障頻度は既定のカテゴリ、見やすさ `[1,10]`、位置付け `[1,10]` です。TOPS上限60は実測最大50に10 TOPSの余裕を持たせます。範囲を超えた値はマッチング時に端点へクリップするため、60 TOPSを超える製品が一般化した際には実機カタログを見て再校正してください。

質問回答から作る顧客側NPU希望値もTOPS単位です。6〜12年使う予定で画像/動画編集、オンライン会議、またはプログラミングを選んだ場合は基礎需要10 TOPS。電源につながず使う頻度と静かな環境で作業する頻度はそれぞれ「ほとんどしない=0」「たまに=10」「頻繁=20 TOPS」を加え、最大50 TOPSにします。これは実機CSVの0/46〜50 TOPSに合わせた初期目安であり、電池持ちや静音を保証する値ではありません。

14項目の重み `[1,1,0.8,0.6,1,0.9,0.7,0.5,1,0.7,0.65,0.55,0.65,0.5]` とランキング式は変えません。QR内の質問コード・ベクトル順・数値だけという形式も変えず、NPU単位が変わったことを区別するためschema versionのみ5にします。

### 8.2 Firestore / スタッフ認証の設定

1. Firebase Consoleで `optimal-pc-proposer` を開き、Authenticationの「メール/パスワード」認証が有効であること、スタッフユーザーが登録済みであることを確認します。
2. Authenticationの設定で公開サイトのホスト `nojimapc2026.github.io`（必要ならカスタムドメインも）を承認済みドメインに登録します。
3. Firestore Databaseの `pc_staff` コレクションに、ログインユーザーの**UIDそのものをドキュメントID**とした文書を管理者権限で1件作成します。例: `pc_staff/<ログインユーザーUID>`。Rulesは文書の存在だけを確認するためフィールドは任意です（例: `{ "enabled": true }`）。この文書はスタッフUIDの許可リストに使われ、自己登録を許可するものではありません。
4. Firestore Database の Rules 画面へ、リポジトリに同梱する `firestore.rules` と同じ内容を貼り付けて「公開」します。`pc_catalog` は読取のみ公開し、create/update/delete は `pc_staff/{request.auth.uid}` が存在するユーザーだけに許可します。全員へ書込みを許す `allow write: if true` は使用しないでください。
5. サインイン後、商品を入力し「新規機種を追加」、続けて「変更を反映」を押します。顧客サイトの推薦は同じ `pc_catalog` を読むため、Firestoreに商品文書が0件なら読み込み自体が成功してもおすすめ商品はありません。

現地のFirebase設定を読み取り専用で確認したところ、未認証の `pc_catalog` list はHTTP 200で成功し、文書数は0件でした。ユーザーのスタッフ認証も成功し、未存在ドキュメントに対する書込権限確認も成功しました。実際の保存エラー `Cannot read properties of undefined (reading 'path')` は旧版スタッフコードがWeb SDK `transaction.get()` にコレクション参照を渡していたことが原因です。更新版は事前にカタログを読み、その後トランザクション内では各 `doc(database,'pc_catalog',jan)` のようなDocumentReferenceを個別に読み直し、JAN重複・編集競合を検証してから書込みます。コード修正だけでなく、新しい `npuTOPS` フィールドに対応するRulesの公開も必要です。

```firestore
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    function isPcStaff() {
      return request.auth != null
        && exists(/databases/$(database)/documents/pc_staff/$(request.auth.uid));
    }
    function validPcRecord(jan) {
      return request.resource.data.keys().hasAll([
        'model','jan','cpuSingle','cpuMulti','npuTOPS','gpu','ramGB','ssdGB',
        'weightG','design','displayInch','aspectRatio','manufacturerMask',
        'failureFrequency','readability','positioning','highlights'
      ])
        && request.resource.data.keys().hasOnly([
          'model','jan','cpuSingle','cpuMulti','npuTOPS','gpu','ramGB','ssdGB',
          'weightG','design','displayInch','aspectRatio','manufacturerMask',
          'failureFrequency','readability','positioning','highlights'
        ])
        && request.resource.data.jan is string
        && (request.resource.data.jan.matches('^[0-9]{8}$') || request.resource.data.jan.matches('^[0-9]{13}$'))
        && request.resource.data.jan == jan
        && request.resource.data.model is string
        && request.resource.data.cpuSingle is number
        && request.resource.data.cpuMulti is number
        && request.resource.data.npuTOPS is number
        && request.resource.data.npuTOPS >= 0
        && request.resource.data.npuTOPS <= 200
        && request.resource.data.gpu is number
        && request.resource.data.ramGB is number
        && request.resource.data.ssdGB is number
        && request.resource.data.weightG is number
        && request.resource.data.design is number
        && request.resource.data.displayInch is number
        && request.resource.data.aspectRatio is number
        && request.resource.data.manufacturerMask is number
        && request.resource.data.failureFrequency is number
        && request.resource.data.readability is number
        && request.resource.data.positioning is number
        && request.resource.data.highlights is string
        && request.resource.data.highlights.size() <= 500;
    }
    match /pc_catalog/{jan} {
      allow get, list: if true;
      allow create, update: if isPcStaff() && validPcRecord(jan);
      allow delete: if isPcStaff();
    }
    match /pc_staff/{uid} {
      allow read, write: if false;
    }
  }
}
```

## 9. QR読取・回答復元・JANカメラ

顧客は数値だけの30列QR（version 5、14ベクトル値、15回答コード）を発行します。version 1〜4はスタッフで引き続き読み取れます。version 2〜4のNPU値は「コア数」単位で作られたため、Q6/Q5/Q9/Q11の格納済み回答コードからTOPS希望を再計算します。回答コードのないversion 1ではNPU TOPS希望を0（指定なし）として扱います。QRの形式、値の順、質問コード15個、QRカメラの仕組みは変更しません。

スタッフのJAN読み取りには、Safari標準 `BarcodeDetector` の有無に依存しないZXing Browser readerを使用します。`@zxing/library@0.23.0` と `@zxing/browser@0.2.1` をJANスキャン開始時だけCDNから読み込み、EAN-13/EAN-8を `TRY_HARDER` で連続解析します。カメラには背面・1920×1080を希望し、端末が対応しない場合は解像度制約を緩和します。JANチェック桁検証、カメラtrackの停止、手入力へのフォールバックは維持します。バーコード全体を横向きで枠に入れ、ピントと光の反射を確認してください。カメラにはHTTPS（GitHub Pages等）とSafari側のサイトカメラ許可が必要です。

デザイン・画面の見やすさ・製品位置付けは販売員が各1〜10で入力します。故障頻度0/1は指定された暫定カテゴリであり、実際の故障統計を表すものではありません。実機カメラ試験は対象iPhone/iPadを直接利用できる環境で最後に確認してください。
